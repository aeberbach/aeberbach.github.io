Code for a Raspberry Pi Pico HID Rudder device.

September 30, 2026 6 min read

(The code that this article discusses is available at my GitHub)

The Raspberry Pi Pico SDK is a very complete package, including tinyUSB by Ha Thach, runs on nearly everything! I'm using it in Visual Studio Code with the official "Raspberry Pi Pico" extension - embedded development does not get easier than this. Install it, create a new project, connect your device and right away you should be able to build and drop the .uf2 image onto the Pico. If you bought the Rapsberry Pi Debug Probe then it's even easier, build and debug with one click, set breakpoints, and you get a serial channel for debugging also. There are many guides on this but I highly recommend the probe, so much for so little money. I have also tried out my Segger J-Link and that works well here too.

Note I am using the Pimoroni Pico Plus 2 - it has clearer labelling and a USB-C port. I have USB-C cables everywhere; I have to look around for a micro-USB these days. It is an excellent product and I can't believe Raspberry Pi are still using micro-USB...

The code does two things really, collect and store values form the three analog-digital converter inputs, and then make USB reports to the connected computer.

ADC

The Pico has three usable ADC channels on board. An early version of this rudder used four channels, one for rudder left and one for rudder right, so I was using an ADS1115 ADC board via I2C. But simple is always better - I switched to one channel for rudder and one for each brake.

There are a couple of ways of getting ADC values. You can simply spin in a loop and read the values as quickly as possible but that wastes a lot of processing time and could easily interfere with the USB reporting. This code uses an interrupt from the ADC FIFO (read the Pico datasheet...) to get the value from the channel and to notify the main loop that a value can be read. An interrupt appears when a channel is selected and the ADC has been instructed to get a value. An ISR should be very short and this just records which channel a value is ready for. Then when the main loop cycles around and detects a ready value, the value is read and stored, the next channel is selected and ADC started and that is all for ADC until the next value appears. The channels are read sequentially, indefinitely. The rudder axis is on GPIO 26, the right brake is on GPIO 27 and the left brake is on GPIO 28.

void adc_isr() {
    // get the value from the ADC that caused the interrupt - this action clears the interrupt
    adc_raw = adc_fifo_get(); 
    // adc_pending is the GPIO from which the interrupt came; main loop will apply adc_raw to
    // that channel when it detects the value of adc_received is no longer zero. 
    adc_received = adc_pending;
}

As each value is read it is added to a buffer of values, with the location beginning at 0 and ending at 9. When the value goes to 10 it loops back to 0 again - in short, a ring buffer. When a value is required all values are summed and then divided by the buffer size to produce and average. In the event of one bad value the output will be less affected. It's a very simple software low-pass filter.

void brake_right_new_value(uint16_t val) {
    static int index = 0;

    brake_right_raw_values[index++] = adc_clamped_value(val, BRAKE_ADC_MIN, BRAKE_ADC_MAX);

    // wrap around to zero if the array is full
    if (index == RAW_VALUE_COUNT) {
        index = 0;
    }
}

uint16_t brake_right_raw_value() {
    uint16_t sum = 0;
    for(int i = 0; i < RAW_VALUE_COUNT; i++) {
        sum += brake_right_raw_values[i];
    }
    return sum/RAW_VALUE_COUNT;
}

When reporting these values the connected machine expects to see values in a range -127..127, so when it is time to output a value the raw ADC values need to be converted. The rudder axis is simple; the ADC value is calculated as a proportion of the full range of values from the lowest to the highest and that is multiplied by 255, that is added to -127 and the output value is ready. This is what using a relatively expensive rotary hall-effect device gets you - it's so simple and reliable that I thought about putting them on the brakes too... but as they say, engineering is the art of doing for $1 what any fool could do for $10.

The brakes are more complex. The result of bringing the magnet close to the hall effect sensor, rotating around a circular path described by the pedal, is not linear. The brake is applied very gradually at first with the transition from about 60% to 100% happening in about the last tenth of rotation, not ideal. In fact the values looked something like this:

What is needed is a function that takes the ADC raw value and produces that proportion of 255 that should be added to -127, just like the rudder axis.

Once, engineers would have drawn a chart and taken their slide rules out. Later they would have fired up Excel. We're able to just use a web site, it's so easy now. I used https://www.standardsapplied.com/nonlinear-curve-fitting-calculator.html - pasting in this table of values and answering a couple of brief questions I got a nice chart instantly, with over 500 equations that could be used, each showing the curve it would produce overlaid on my data points. The very first one, and best fit, was

y = 0.2009032376 * asinh(5763.173774 * x^(1/4) - 680.1121958 * x^(1/2) + 3.331253105 * x - 14004.61103) - 0.6830070089

and some are even more complex. The brake function does not need to be perfect, so I took one reported as the 7th best match - it looked smooth, and is not very difficult for the Pico to compute:

y = 0.1746403809 * ln(x - 724.7640485) - 0.437040687

With this the y value is a simple float that can be used as a proportion for reporting brake position in the range -127..127.

int fitted_raw_brake_value(int raw) {
    float adjusted = 0.1746403809 * log((double)raw - 724.7640485) - 0.437040687;
    // if it's greater than 1.0, use 1.0; if less than 0.0, use 0.0
    float clamped_adjusted = MAX(MIN(adjusted, 1.0), 0.0);

    // the minimum joystick axis value is -127, maximum is 127. The brake at rest should
    // report -127 and as it is applied that value increases. An offset of 0..255 is added
    // based on the relative position of the brake pedal.
    int brake_value = (int)(-127.0 + (clamped_adjusted * 255.0));

    return brake_value;
}

Of course there are imperfections everywhere here. The function is not perfect even ignoring that the values probably do not naturally stop at 6-9 decimal places, the two brakes are not exactly the same and many more issues... but all this is reduced to 255 possible values, and calibration allows all the imprecisions to be ignored.

Almost no input device would actually present a range of values -127..127, and very few would report 0 when at rest. This is why you have a means to calibrate the input device either at the OS level (like Windows input controller properties) or in the application (Microsoft Flight Simulator control setup) - or maybe your software just observes values all the time and calibrates without you even being told about it. Calibration routines have you move the control through its range of values and then the input is scaled further before use. The actual value sent by the input controller might be -109..83 with a centre point of -6 and that gets adjusted, in software, before use. (This is why the rudder works almost equally well with a 360 degree hall effect device, or a plain potentiometer, where the raw ADC values might range from 2100..2750 rather than 750..4096).

USB

So, with the values all ready to go how do they get to the computer? USB is a complicated thing, but there is a class of devices within USB called Human Interface Device for which nearly all machines already have a driver, and you can use that for gamepads, keyboards, mice, rudders, joysticks, macro pads, etc. All you need to do is report the correct descriptors, so some power-state housekeeping, and then respond to the hid report with the correct values.

That last sentence above is doing an awful lot of work but I don't want to go into more explanation. I don't know if I am qualified, but I do have the excellent "USB Complete: The Developer's Guide, Fifth Edition" by Jan Axelson and it has been able to answer every question. If you just want to make and use a device you can probably get by with just using an example. It only gets complicated when you step into the less-defined classes. It also gets more complicated if you want to use a driver other than the one provided by the OS - such a driver is selected based on the device descriptor being a better match, and can get you a fancy display of the actual device on-screen, much like the excellent Honeycomb flight controls do. I have not done this!
